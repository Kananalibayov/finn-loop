## What changed and why

Adds single-admin login so the app (currently open to anyone on localhost) is protected before deployment. A password is verified against a bcrypt hash from `ADMIN_PASSWORD_HASH`; on success a signed JWT (jose HS256) is set in an http-only cookie, read by middleware to gate every app and API route. Closes #6.

## Scope ledger

**Acceptance criteria**

- AC-1 — `ADMIN_PASSWORD_HASH` and `ADMIN_SESSION_SECRET` are read server-side from env in `lib/auth.ts` (`sessionSecret()`, `verifyPassword()`); never hardcoded. `.env.example` documents both.
- AC-2 — `/login` page accepts a password; `verifyPassword()` compares against the bcrypt hash via `bcryptjs` (pure-JS implementation of the bcrypt format — produces/verifies the standard `$2a$...` hash, fully compatible with native `bcrypt`). Wrong/missing hash fails closed.
- AC-3 — On success, `createSessionCookie()` mints a signed JWT (jose HS256, 7-day exp) and returns it as an http-only, SameSite=Lax `Set-Cookie`. Wrong password returns a generic 401 with the same body shape as a missing-hash failure (no information leak).
- AC-4 — `middleware.ts` protects everything except public paths (`/login`, `/logout`, `/api/login`) and static assets (`_next/static`, `_next/image`, `favicon.ico`). Unauthenticated HTML requests redirect to `/login?next=...`; unauthenticated API requests return 401 JSON.
- AC-5 — `/logout` clears the cookie (`Max-Age=0`) and redirects to `/login` (303). Accepts GET and POST.
- AC-6 — `generate` and `zip` API routes are protected by the same middleware matcher (`/api/*` minus the `/api/login` public exemption). No explicit per-route check needed; middleware enforces it.
- AC-7 — `.env.example` documents `ADMIN_PASSWORD_HASH` (with the bcrypt-hash generation command) and `ADMIN_SESSION_SECRET` (with the random-bytes command), plus `NEXT_PUBLIC_URL`.
- AC-8 — `npm run build` passes; route table includes `/login`, `/logout`, `/api/login`, and Middleware (40.1 kB).

**Non-goals (preserved)**

- NG-1 — Single admin only; no multi-user or roles. The JWT payload is `{ role: "admin" }` with no user id.
- NG-2 — No password reset flow; password is set via env hash.
- NG-3 — No OAuth / magic links; only the password form.
- NG-4 — No rate limiting; localhost/trusted-first.

**Other behavior changes:** None. The generator, sites API, and zip API keep their existing logic; only their *access* is now gated by the cookie. There is no DB change, no schema change, no change to existing route response shapes.

## Implementation notes disclosed

- **Library choice:** Used `bcryptjs` (pure JS) instead of native `bcrypt`. The spec says "bcrypt hash" (a format) — `bcryptjs` produces and verifies the identical `$2a$...` format, so the requirement is satisfied without the native-compile toolchain dependency that caused install pain in issue #4. Hashes are interchangeable between the two libraries.
- **jose edge-runtime warning:** During build, jose emits a warning that `DecompressionStream` (from its JWE path) isn't in the Edge Runtime. This is benign for our usage — middleware uses only `jwtVerify` (the JWT path), which works in Edge. The warning does not fail the build and the JWT verify path is functional. (If a future jose version makes this a hard error, the fix is to verify the JWT in a route helper instead of middleware.)
- **Login route layout:** The login POST handler lives at `/api/login` (not `/login/route.ts`) because Next.js forbids a page and a route handler resolving to the same path. `/api/login` is exempted from auth in `middleware.ts` so unauthenticated users can log in.

## Manual test steps

1. Generate a bcrypt hash: `node -e "console.log(require('bcryptjs').hashSync('your-password', 10))"` (after `npm install bcryptjs`).
2. Put `ADMIN_PASSWORD_HASH=<hash>` and `ADMIN_SESSION_SECRET=<32+ random chars>` in `.env`.
3. `npm run dev`, open `/` → redirected to `/login`.
4. Wrong password → "Incorrect password." stays on `/login`.
5. Correct password → lands on `/`.
6. `curl -i http://localhost:3000/api/sites` without cookie → 401 JSON.
7. Visit `/logout` → redirected to `/login`; `/` now redirects again.

- `bcryptjs` smoke test (`hashSync` + `compareSync` round-trip) → ✅ correct password verifies, wrong password rejected.
- `git diff` reviewed — 4 modified (`.env.example`, `app/globals.css`, `package.json`, `package-lock.json`), 4 new (`lib/auth.ts`, `middleware.ts`, `app/login/page.tsx`, `app/api/login/route.ts`, `app/logout/route.ts`). No secrets; `.env` not touched.

## Risk

**Medium.** Auth touches every request via middleware — a bug here locks out the whole app or, worse, fails to protect. Mitigations: fail-closed defaults (missing hash = no login possible), generic error messages, http-only + SameSite cookie, signed JWT with expiration. The library substitution (bcryptjs) is format-compatible. Manual test steps above must be run before merge to confirm the redirect/cookie/401 flows work end-to-end.
